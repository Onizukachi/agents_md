# LT-54055 — Субагенты: уведомление по почте о пополнении баланса

## Problem

Субагенты пополняют депозитный счёт Академии Сервиса банковским переводом. По LT-53705 записи о пополнении (`deposit_transactions`) уже создаются автоматически по выписке Альфа-Банка, но субагент об этом никак не узнаёт — казначей сообщает о зачислении вручную или не сообщает вовсе.

Нужно после автоматического зачисления отправлять субагенту согласованное письмо. Текст, тема и получатели у каждого субагента свои и меняются без участия разработчика, поэтому зашивать их в код нельзя.

Параллельно вскрылось, что механика LT-53705 написана под одного партнёра: имя партнёра, имя плательщика и юрлицо — три константы в сервисе. Появился второй субагент (Тревел Солюшенс), и его платежи тоже нужно превращать в пополнения. Без универсализации каждый следующий субагент — это правка кода.

## Solution

1. Таблица `partner_notification_email_templates` — конфигурация писем: получатели, отправитель, тема и тело с поддержкой переменных `{{...}}`, привязка к партнёру и к виду события (`kind`). Заполняется казначейством через ActiveAdmin.
2. `DepositTransactions::CreateFromAlfaAccountTransactions` переводится на список правил матчинга: партнёр, ИНН плательщика, юрлицо и опциональные условия по назначению платежа и сумме.
3. После создания записи о пополнении ставится задача на отправку письма. Факт отправки фиксируется в `deposit_transactions.notified_at`, чтобы письмо ушло ровно один раз.

## Scenarios

1. Кредитовая операция от ИНН 7705859041 на сумму ≥ 1 000 000 ₽, в назначении нет «Счет-фактура» → создаётся `DepositTransaction` (партнёр 1163, `inflow`, юрлицо AK) и ставится задача на письмо.
2. Кредитовая операция от ИНН 7705859041 на 82 800 ₽ с «Счет-фактура» в назначении → ничего не создаётся.
3. Кредитовая операция от ИНН 7705859041 на 530 083 ₽ без «Счет-фактура» в назначении → ничего не создаётся (отсекает порог суммы).
4. Кредитовая операция от ИНН 7705859041 под альтернативным написанием имени (`Интернет Трэвел, ООО`), сумма ≥ порога, назначение чистое → создаётся; матчинг по ИНН, имя не участвует.
5. Кредитовая операция от ИНН 7736377030 с `Оплата Обеспечительного платежа по п. 6.1.` в назначении → создаётся `DepositTransaction` для партнёра 1340.
6. Кредитовая операция от ИНН 7736377030 на 1 ₽ с назначением про оплату заказа → ничего не создаётся: положительная маска не совпала. Порог суммы для этого партнёра не применяется.
7. Маска назначения сравнивается без учёта регистра (`СЧЕТ-ФАКТУРА`, `счёт-фактура` — то же самое).
8. Операция, у которой уже есть связанная запись пополнения → повторно не создаётся и повторного письма не порождает.
9. Дебетовая операция, операция вне временного окна, операция с пустой суммой → не рассматриваются.
10. Создано пополнение, для партнёра есть активный шаблон `deposit_inflow` → уходит письмо на адреса из `to`, от адреса из `from`, с темой и телом, где подставлены значения переменных; `notified_at` заполняется.
11. Создано пополнение, шаблона для партнёра нет или он неактивен → письмо не уходит, запись остаётся с пустым `notified_at`, в лог пишется `info`, Sentry не дёргается.
12. Задача на отправку выполняется повторно (ретрай Sidekiq) для записи с заполненным `notified_at` → письмо не дублируется.
13. Тело шаблона содержит переменную, которой нет в списке доступных → остаётся в тексте как есть, отправка не падает.
14. Шаблон сохраняется с адресами, записанными через запятую с лишними пробелами и дублями → адреса нормализуются; невалидный адрес не даёт сохранить запись.
15. Попытка завести второй шаблон с тем же `kind` и тем же партнёром → отклоняется.
16. Разовый таск проставляет `notified_at` историческим записям со связью → повторный запуск воркера по ним письма не отправляет.
17. Разовый таск связывает ручные пополнения с alfa-транзакциями → последующий прогон сервиса не создаёт по ним дублей.

## Implementation decisions

### Схема

**`partner_notification_email_templates`**

| колонка | тип | примечание |
|---|---|---|
| `kind` | string, not null | пока единственное значение `deposit_inflow` |
| `partner_id` | integer, not null | |
| `name` | string | человекочитаемое имя для админки |
| `from` | string, not null | дефолт `system@level.travel` |
| `to` | text, not null | адреса через запятую |
| `subject` | string, not null | поддерживает `{{...}}` |
| `body` | text, not null | plain text, поддерживает `{{...}}` |
| `active` | boolean, not null, default true | |

Уникальный индекс `(kind, partner_id)`. Колонок `cc`/`bcc` нет.

**`deposit_transactions.notified_at`** — `datetime`, nullable, **без индекса**. Колонка фиксирует факт отправки и защищает от повторной; по ней ничего не выбирается. `notified_at IS NULL` **не** означает «письмо надо дослать» — у записей без шаблона она остаётся пустой навсегда. Это должно быть зафиксировано комментарием в коде.

Миграции — в стиле проекта: `safety_assured` и guard'ы `column_exists?` / `index_exists?`.

### Правила матчинга

Список правил — константа сервиса (отдельная таблица сознательно не заводится). Поля правила: `partner_id`, `payer_inn`, `organization_id`, опционально `payment_purpose_mask` (положительная), `excluded_payment_purpose` (отрицательная), `min_amount`.

| | Озон | Тревел Солюшенс |
|---|---|---|
| `partner_id` | 1163 | 1340 |
| `payer_inn` | `7705859041` | `7736377030` |
| `organization_id` | `Organization::AK` | `Organization::AK` |
| назначение | исключить `Счет-фактура` | требовать `Оплата Обеспечительного платежа по п. 6.1.` |
| порог суммы | `>= 1_000_000` | — |

Матчинг по `payerInn`, а не по `payerName`: имя нестабильно (три написания у одного ИНН) и уже стоило пропущенного пополнения. ИНН состоит из цифр, поэтому бинарная коллация `JSON_UNQUOTE` роли не играет и `COLLATE` не нужен. Маски по `payment_purpose` — обычный `LIKE` по колонке с `_ai_ci` (регистронезависимо из коробки), значение прогоняется через `sanitize_sql_like`.

Партнёр ищется по `id`, имя партнёра остаётся комментарием рядом с правилом. Окно выборки, дедупликация через `left_joins` и остальные условия сохраняются как есть.

Сервис перестаёт считать `created` по числу итераций и считает фактически созданные записи — это требуется, чтобы письмо ставилось в очередь только на реально созданное пополнение.

### Шаблоны и рендеринг

Модель шаблона: `enum :kind`, валидации обязательных полей, уникальность `partner_id` в пределах `kind`, нормализация `to` перед валидацией (разбор по разделителям, удаление дублей и пустых, склейка обратно), проверка каждого адреса, метод для получения списка адресов массивом, скоуп активных, и метод получения доступных переменных по `kind` — калькой с `OperatorTemplate.available_variables_for_kind`.

Рендерер вида `deposit_inflow` подставляет `{{...}}` тем же способом, что и `OperatorTemplates::BaseContentRenderer`, и применяется и к теме, и к телу. Базового класса рендереров не заводим, пока вид один.

Доступные переменные: `amount` (сумма пополнения, формат `5 000 000,00` — разделители задаются явно, без опоры на локаль), `amount_ru_propis` (сумма прописью), `operation_date` (дата банковской операции), `payment_purpose` (назначение платежа), `today_date`. Текущий остаток депозита в переменные **не** выносится.

Неизвестная переменная в шаблоне остаётся в тексте нетронутой.

### Отправка

Отдельный воркер принимает id пополнения и: выходит, если `notified_at` заполнен; ищет активный шаблон по паре (`deposit_inflow`, партнёр) и выходит с записью в лог, если шаблона нет; рендерит и отправляет письмо; затем проставляет `notified_at`. Ошибки — в Sentry с перевыбросом, как в соседнем воркере; ретрай Sidekiq безопасен за счёт guard'а.

Письмо — multipart: текстовая часть как есть, html-часть через `simple_format`. Отправка из воркера синхронная (`deliver_now`), чтобы `notified_at` фиксировал факт отправки, а не постановки в очередь.

Сервис ставит задачу на отправку после создания каждой записи.

### Админка

Страница шаблонов в меню **«Продажи»** (рядом с «Депозитный счёт»), а не в «Контент»: заполняют казначеи. Под формой — панель доступных переменных вида, как в админке операторских шаблонов. **Предпросмотр** рендерит письмо на странице шаблона по последнему пополнению партнёра — кому, от кого, тема и текст с подставленными значениями; реальной тестовой отправки нет — оба шаблона бьют по внешним адресам. Переводы модели и атрибутов — в `config/locales/ru.yml`.

Реализовано панелью на странице просмотра, а не отдельным действием с кнопкой: результат тот же, но без лишнего маршрута и шаблона вьюхи.

### Разовые таски

Три таска в namespace `one_time`, каждый идемпотентный:

1. **Связывание** ручных пополнений с alfa-транзакциями по правилам матчинга — обобщение логики коммита b5c20f4 (кандидаты по сумме и окну `±1 день`, отказ при неоднозначности, сводка по пропущенным).
2. **Пометка истории**: `notified_at` проставляется записям с заполненным `alfa_account_transaction_id`, созданным **раньше обязательной границы `CUTOFF`**. Без этого «пустой `notified_at`» у 69 исторических строк выглядит как «кому-то не отправили». Граница обязательна и без неё таск отказывается работать: иначе он пометит и пополнения, которые новый код создал минуту назад и по которым письмо ещё лежит в очереди или в ретрае, — такое письмо после пометки молча не уйдёт.
3. **Заведение шаблонов** — две строки через `find_or_create_by`, чтобы повторный прогон не затирал правки казначеев.

Содержимое шаблонов:

### Порядок выката

Рекомендуется два деплоя:

1. Миграции и разовые таски (правила матчинга не меняются, поведение прежнее) → прогнать таски связывания и пометки истории, разобрать списки пропущенных записей.
2. Новые правила матчинга, воркер и отправка → затем таск с шаблонами.

Причина: ручное пополнение 53811 (TS) и alfa 348167 (Озон, 6 млн) попадают в окно выборки и без предварительного связывания дадут дубли, а по TS ещё и письмо. Пока шаблонов нет, письма не уходят — это страхует от ошибки в порядке.

Одним деплоем тоже допустимо, но таск связывания нужно прогнать до следующего тика крона, то есть в пределах трёх часов.

## Testing decisions

Тестируем внешнее поведение на трёх швах, от высокого уровня к низкому. Рендерер и мейлер отдельными швами не выносим — они проверяются через воркер по фактическому содержимому письма.

1. **Сервис** (`DepositTransactions::CreateFromAlfaAccountTransactions.call`) — главный шов. На входе записи `alfa_account_transactions`, на выходе созданные `deposit_transactions` и поставленные задачи на отправку. Покрывает сценарии 1–9: оба правила, обе маски, порог суммы, регистронезависимость, дедупликацию, отсечение дебета/окна/пустой суммы. Сюда же регрессионные кейсы из реальных данных: платёж на 1 ₽ от Тревел Солюшенс и платёж 530 083 ₽ от Озона.
2. **Воркер отправки** — на входе пополнение и шаблон, на выходе письмо в `ActionMailer::Base.deliveries` и состояние `notified_at`. Покрывает сценарии 10–13: адресаты, отправитель, тема и тело с подставленными переменными, отсутствие шаблона, повторный запуск, неизвестная переменная.
3. **Модель шаблона** — нормализация и валидация списка адресов, уникальность пары `kind` + партнёр (сценарии 14–15). Чистая логика, дешёвый шов.

Разовые таски (сценарии 16–17) тестами не покрываем — это одноразовый код, как и остальные в `one_time`.

Нужны фабрики для модели шаблона и для `DepositTransaction` — последней в проекте нет. Фабрики `alfa_account`, `alfa_account_transaction`, `partner` и `organization` уже есть в `spec/factories/`. Прототип для спеки сервиса — `spec/services/alfabank/h2h/account_transactions_synchronizer_spec.rb`. `describe` / `context` / `it` пишутся по-английски.

## Out of scope

- Письма по пополнениям, заведённым казначеем вручную в админке: триггер — только автоматическое создание из выписки.
- Агрегированное письмо на несколько транзакций: за один прогон исторически всегда приходит ровно одна.
- Отдельная таблица правил матчинга партнёр ↔ плательщик: решено держать в коде.
- Догрузка исторических платежей Тревел Солюшенс: истории нет, окно выборки остаётся прежним.
- Текущий остаток депозита в письме.
- Кнопка реальной тестовой отправки в админке.
- `cc` / `bcc` в шаблоне.
- Разбор шести крупных платежей Озона без связи — выполняется вручную по итогам прогона таска связывания.
- `CONTEXT.md` в корне репозитория.

## Further notes

- Матчинг по имени плательщика работал как фильтр **побочно**: счета-фактуры Озона приходят под коротким написанием имени, а пополнения — под полным. Это совпадение, а не правило, и оно уже сломалось (alfa 122386). Стоит зафиксировать комментарием у правила, чтобы следующий разработчик не счёл переход на ИНН избыточным.
- Отсутствие письма не означает отсутствия платежа: при промахе правила казначей заводит пополнение руками, как делал всё время до автоматизации. На письма нельзя опираться как на полный перечень пополнений — это надо проговорить казначейству.
- Альтернативы правилу для Озона, проверенные на данных: положительная маска `%продажа авиабилетов%` теряет 2 пополнения из 75; маска `%НДС не обл%` даёт 75 из 75 при нуле ложных, но по всей таблице совпадает с 782 строками у 15 плательщиков. Выбран вариант «исключить счёт-фактуру + порог суммы» — два условия разной природы, закрывающие слепые зоны друг друга.
- Маску нельзя строить на строке `Оплата по договору 01/04/2026 от 01.04.2026 продажа авиабилетов`: в данных между датой и словом «продажа» стоят два или три пробела, и маска с одинарным пробелом не совпадёт ни с одной строкой. Кроме того, номер договора меняется при перезаключении, и правило сломается молча.
- `deposit_transactions.amount` — `DECIMAL(10,0)`, то есть копейки в сумме пополнения теряются ещё на этапе LT-53705; в письме сумма форматируется из этого значения.

## Итоги ревью

Оба прохода гейта `leveltravel-pr-review` пройдены. Исправлено по их находкам:

- Тестовая дыра: четыре переменные из пяти и весь путь подстановки в **тему** письма ничем не проверялись — удаление `render_content` из темы оставляло набор зелёным. Добавлен сценарий со всеми пятью переменными и переменной в теме, время стабилизировано `travel_to`.
- Подсказка для `amount_ru_propis` в админке обещала формат `(Пять миллионов рублей 00 копеек)`, а `RuPropisju.rublej` на целых рублях копейки не печатает (проверено прогоном: `5000000 → «пять миллионов рублей»`). Пример в подсказке исправлен.
- `Partner.find` вызывался до выборки транзакций: на базе без партнёра 1340 прогон падал каждые три часа вхолостую. Поиск партнёра стал ленивым — падает громко, но только когда действительно есть что создавать.
- `mark_deposit_transactions_notified` получил обязательную границу `CUTOFF` (см. выше).
- Убраны мёртвые ветки: недостижимый `|| Time.current` в дате операции и проверка присутствия `from`, которую до неё же заполняет `set_default_from`.
- Цикл по видам в форме админки рендерил ровно одну панель и дублировал блок со страницы просмотра — заменён одной панелью.
- В таск заведения шаблонов добавлено предупреждение: на staging воркеры выполняются синхронно и перехвата получателей нет, поэтому заведённый там шаблон отправит настоящее письмо на внешние адреса.

Осознанно не исправлено:

- **Правило Озона — чёрный список, а не белый.** Любой платёж от ИНН 7705859041 на сумму ≥ 1 млн с иным назначением станет пополнением и письмом. Решение принято по данным: положительная маска `%продажа авиабилетов%` теряет два настоящих пополнения из 75, чёрный список с порогом — ноль ошибок на полугодовой истории.
- **`deliver_now` до простановки `notified_at`.** Это осознанный выбор «хотя бы один раз»: при сбое доставки письмо уйдёт на ретрае. Обратный порядок дал бы «не более одного раза» и тихую потерю письма при сбое SMTP, что для уведомления о деньгах хуже дубля.
- **`organization_id` в правиле при единственном значении `AK`.** Оставлено осознанно: это поле правила, а не константа сервиса, и оно же задаёт область поиска в таске связывания.
- **Копейки.** `deposit_transactions.amount` — `DECIMAL(10,0)`, копейки банковского перевода теряются ещё на LT-53705. Письмо сообщает сумму, зачисленную на депозит, то есть согласовано с балансом партнёра. Само округление — отдельный дефект LT-53705, заводить отдельной задачей.
- **Предпросмотр в админке жёстко использует рендерер вида `deposit_inflow`.** Вид один; при появлении второго правятся мейлер и предпросмотр вместе.

Не проверено никем: отрисовка страницы админки в браузере и реальная доставка SMTP.
