# Загрузка новых реестров партнёров + Дата проведения

Tracker: LT-53571

## 1. Бизнес-контекст

`RegistryFile` — загруженный вручную через ActiveAdmin файл сверки/реестра от
партнёра. `PartnerRegistries::ProcessFileWorker` разбирает его через
`PartnerRegistries::Processor`, который выбирает `Rules::*`-класс по
`partner.registry_processor` и создаёт `PartnerOperation` на каждую строку.
Сейчас у всех настроенных партнёров реестр — это банковская сверка
транзакций: заказ ищется по RRN через `Payment`, а сумма комиссии считается
по транзакции.

Восемь новых партнёров (Getblogger, Альфа-Тревел, Ozon/Интернет Трэвел,
Мосгортур, CRPO, Яндекс Путешествия, Т-Путешествия, Туту) присылают реестры
другого рода: номер заказа уже известен из файла напрямую, искать его через
RRN/платёж не требуется — нужны только номер заказа и сумма комиссии.
Формат колонок у каждого партнёра свой. Отдельно, реестр партнёра
Getblogger (partner_id=6) может приходить в двух разных форматах: обычный
Getblogger-формат и универсальный формат «Сверка Партнёры», который содержит
операции сразу нескольких реальных партнёров.

Дополнительно бухгалтерии нужна возможность проставлять и позже
редактировать в карточке загруженного реестра дату отчётного периода
(«Дата проведения»), которой сейчас в `RegistryFile` нет.

## 2. Результат и границы задачи

### Ожидаемый результат

- В ActiveAdmin можно загрузить реестр любого из 8 партнёров, и по каждой
  строке файла корректно создаётся `PartnerOperation` с верными `order_id` и
  `cost`.
- При загрузке можно указать «Дата проведения»; после загрузки это поле
  можно посмотреть и отредактировать отдельно от остальных данных реестра.
- Для реестра партнёра 6 (LevelTravel) оба формата файла обрабатываются
  одним обработчиком; у созданных операций `partner_id` берётся из
  `order.partner_id`, а если у заказа партнёр не указан — используется 6.
- Готов rake task, которым можно проставить нужный `registry_processor`
  нужным партнёрам в любом окружении (dev/staging/production) одним
  прогоном.

### Входит в задачу

- Миграция: колонка `accounting_date` (date, nullable) в `registry_files`.
- `app/admin/registry_files.rb`: date-инпут «Дата проведения» в форме
  загрузки, `:edit`-экшен с формой только для `accounting_date`,
  `permit_params`, вывод поля в `index` и `show`.
- Новые `Rules::*`-классы под реальные форматы файлов:
  `AlfaTravel` (1220), `Mosgortur` (1297), `YandexTravel` (73), `TTravel`
  (1190), `Tutu` (47), `CrpoPP` (1193), `LevelTravel` (6, два формата в
  одном классе, полностью свой `#process`, без изменений в `Base`).
- Rake task, проставляющий `registry_processor` нужным партнёрам (6,
  1220, 1297, 1193, 73, 1190, 47) значениями, совпадающими с именами
  классов (`LevelTravel`, `AlfaTravel`, `Mosgortur`, `CrpoPP`,
  `YandexTravel`, `TTravel`, `Tutu`) — вызывается вручную в нужном
  окружении, не запускается автоматически при деплое/миграции.
- Проверка (без изменения кода), что партнёр 1163 (`ozon_api`, уже
  настроен на `OzonApi`) корректно обрабатывает реальный образец файла
  Ozon/Интернет Трэвел.
- Фокусные специи (готовые Ruby-хеши как строки реестра, без файловых
  фикстур) на новые Rule-классы и на миграцию.

### Не входит в задачу

- Партнёры 1044 (`CRPO`) и 1150 (`ozon_travel`) — в исходной постановке
  были перепутаны с 1193/1163, в задачу не входят и не трогаются.
- Автоматический запуск rake-таска при деплое/миграции — таск ложится в
  код, но включение `registry_processor` в каждом окружении (включая
  production) остаётся осознанным ручным действием того, кто его
  запускает.
- RSpec-специи и ручная UI-проверка `app/admin/registry_files.rb`
  (загрузка/edit `accounting_date`) — по явному решению пользователя не
  делаем, ограничиваемся фокусными спеками на Rule-классы и миграцию.
- Remote gate TeamCity `rails-rspec` как обязательное условие готовности —
  по явному решению пользователя для этой задачи не требуется.
- Фильтрация строк реестра по статусу заказа (`canceled`/`got_back` и т.п.)
  — импортируются все строки как есть.
- Изменение `cost_ratio_for`/НДС-логики — остаётся как есть для всех новых
  партнёров (no-op, пока партнёру явно не задан `vat_rate`).
- Изменение `PartnerRegistries::Rules::Base` — по явному решению
  пользователя базовый класс не трогаем вообще (см. «Ключевые решения»);
  партнёр 6 полностью переопределяет `#process` в своём классе.
- Изменение существующих банковских `Rules::*` (TBank, Sber, Vtb, Halva,
  Psb, Raiffeisen, Bks, Mkb) и их поведения.
- Переиспользование или изменение существующего пустого класса `Crpo` —
  он остаётся как был, никому не назначен; для партнёра 1193 заведён
  отдельный новый класс `CrpoPP`.
- Обратное связывание `Payment` (`extract_rrn` ищет `Payment` по `order_id`)
  — поведение уже есть в `GeneratedRegistries`, новые классы просто
  наследуют его без изменений.

### Критерии готовности

- Тестовая загрузка каждого из 8 образцов файлов (`~/Downloads/repo_uploads`)
  в дев-окружении создаёт `PartnerOperation` с ожидаемыми `order_id`/`cost`
  для каждой строки, без ошибок обработки.
- Для универсального формата «Сверка Партнёры» операция получает
  `partner_id`, равный `order.partner_id` найденного заказа (или 6, если
  заказ не найден/у заказа нет партнёра); для обычного Getblogger-формата
  действует та же логика.
- `PartnerRegistries::Rules::Base` и все существующие банковские правила
  остаются байт-в-байт как были (нет ни одной строки диффа).
- В ActiveAdmin `RegistryFile` дата «Дата проведения» сохраняется при
  загрузке, видна в `index`/`show`, редактируется через `:edit` без
  возможности поменять файл/партнёра/статус.
- Миграция применена, `db/schema.rb` содержит только релевантное изменение.
- Rake task при запуске в дев-окружении корректно проставляет
  `registry_processor` всем 7 целевым партнёрам (проверено live-запросом
  до/после).
- Локальные фокусные тесты зелёные, пройден read-only review.

### Предположения

- Назначение `registry_processor` — через rake task (код, ревьюится и
  переиспользуется в любом окружении), а не через data-миграцию, чтобы
  включение в production оставалось отдельным осознанным действием, а не
  побочным эффектом деплоя.
- Значения `registry_processor` — точное имя класса (`LevelTravel`,
  `AlfaTravel`, ...), как уже принято у всех существующих партнёров
  (`TBank`, `Sber`, `OzonApi`, `GeneratedRegistries` и т.д.), а не
  snake_case-строка — `Partner#class_registry_processor` просто вызывает
  `.camelize`, что на уже-PascalCase строке не меняет её (проверено в
  rails runner, включая двойную заглавную `CrpoPP`).
- Специи бьют по `#process(row)` напрямую с готовыми Ruby-хешами — файловые
  фикстуры (даже синтетические `.xlsx`/`.csv`) не нужны вовсе, реальные
  скачанные файлы (могут содержать `ID_клиента` и т.п.) в репозиторий не
  попадают.
- Дата-колонка для расчёта `repo_date` у партнёров, где в исходной таблице
  пользователя явно не указана колонка даты, берётся по наиболее очевидному
  столбцу файла: Альфа-Тревел — «Дата операции», Мосгортур — «Дата заказа»,
  CRPO/Ozon — «Дата создания заказа» (уже в `GeneratedRegistries`), Яндекс —
  «дата», Т-Путешествия — «Дата», Туту — «Дата заказа», Getblogger —
  «Дата»/`order_date` (совпадают), универсальный формат — «Дата создания».
- `HEADER_SEARCH` новым классам не нужен — во всех образцах заголовки
  находятся в первой строке листа.

### Открытые вопросы

Нет.

## 3. Текущее устройство системы

- `app/workers/partner_registries/process_file_worker.rb:7-30` — скачивает
  файл `RegistryFile`, вызывает `PartnerRegistries::Processor`.
- `app/services/partner_registries/processor.rb:11-25` — берёт Rule-класс
  через `partner.class_registry_processor(is_kb)`, читает файл
  `Spreadsheet::Reader.read` с `READ_SCHEMA`/`HEADER_SEARCH` класса, вызывает
  `rule.process(row)` на каждой строке в транзакции.
- `app/models/partner.rb:742-748` — `class_registry_processor` резолвит
  `registry_processor`-строку (`camelize`) в класс
  `PartnerRegistries::Rules::<Class>`.
- `app/services/partner_registries/rules/base.rb:11-39` — `#process`:
  извлекает RRN/дату/сумму, ищет `Payment` по RRN или по логам платежей за
  окно дат, из платежа берёт `order_id`, создаёт `PartnerOperation` с
  **хардкодом** `partner_id: @partner.id` (строка 27). Рассчитан на
  банковские сверки транзакций (TBank/Sber/Vtb/Halva/Psb/Raiffeisen/
  Bks/Mkb), где номера заказа в файле нет.
- `app/services/partner_registries/rules/generated_registries.rb` — уже
  существующий подкласс `Base`, читающий `order_id` **напрямую из строки**
  (`find_order_id` → `row['Номер заказа']`), а `extract_rrn` работает в
  обратную сторону: ищет `Payment` по `order_id`, а не наоборот. Именно эта
  форма нужна всем новым партнёрам. `READ_SCHEMA` уже соответствует формату
  Ozon (1163) и CRPO (1193): `Номер заказа` / `Дата создания заказа` /
  `Комиссия партнера:итого`.
- `app/services/partner_registries/rules/crpo.rb`,
  `.../rules/ozon_api.rb` — пустые подклассы `GeneratedRegistries`, уже в
  коде, но **ни один партнёр** из задачи их не использовал на момент
  исследования, кроме partner_id=1163 (`ozon_api`), у которого
  `registry_processor = "OzonApi"` уже стоит.
- `app/services/spreadsheet/reader.rb` и `type_castable.rb` — заголовок
  считается первой строкой листа, если `HEADER_SEARCH` не задан; пробелы в
  заголовках схлопываются (`normalize_header`), `Float`-каст понимает
  запятую как разделитель; `Date.parse("26-07-01")` корректно даёт
  `2026-07-01` (проверено в rails runner).
- `app/admin/registry_files.rb` — `actions :index, :show, :destroy` (нет
  `:edit`), форма загрузки в `sidebar` собирает `partner_select`/`is_kb`/
  `file` через `collection_action :upload` (строки 126-169), сохраняет
  `RegistryFile.create!` без `accounting_date`.
- `db/schema.rb:6300-6310` — `registry_files`: нет колонки `accounting_date`.
- `orders.partner_id` (`db/schema.rb:4899`) — колонка есть, используется как

- `lib/tasks/partner.rake` — существующий пример rake-таска в namespace
  `partners`, обновляющего `Partner` через `update_columns` — образец стиля

- Проверено живым запросом в `lt.rails`: ни у одного из партнёров

## 4. Ключевые решения

**`Rules::Base` не трогаем вообще; `LevelTravel` вызывает `super`, а не
дублирует `#process`.**
Первая версия добавляла в `Base` protected-хук `operation_partner_id(order)`
— пользователь попросил убрать: `Base` должен по умолчанию всегда брать
`partner_id` из реестра «как раньше», без индирекции ради одного
класса-исключения. Второй вариант (отклонён пользователем) — полностью
скопировать тело `Base#process` в `LevelTravel` с одной изменённой строкой:
пользователь спросил, зачем копировать всё, и был прав — это тянет за
собой RRN/payment-логику `Base` текстом, а не переиспользованием, и любое
будущее изменение `Base#process` придётся вручную синхронизировать в двух
местах. **Итоговая версия**: `LevelTravel#process` вызывает `super` (создаёт
`PartnerOperation` как обычно, `partner_id: @partner.id`), затем
`assign_order_partner_id(row)` точечно переставляет `partner_id` на
`order.partner_id` через `.where(order_id: order_id).update_all(...)`, если
у найденного заказа партнёр указан. Ни строчки из `Base#process` не
скопировано; `Base` не тронут вообще.

**Все новые Rule-классы (кроме `LevelTravel`) наследуются от
`GeneratedRegistries`, а не от `Base` напрямую.**
`GeneratedRegistries` уже реализует нужный паттерн «`order_id` известен из
файла, RRN ищется в обратную сторону через `Payment.find_by(order_id:)`» и
его не нужно менять. Переопределять нужно только `READ_SCHEMA`,
`find_order_id` и `calculate_base_cost` (плюс `extract_date`, если имя
колонки отличается от «Дата создания заказа»).

**Партнёр 6 — класс `LevelTravel` (не `Getblogger`), один
`READ_SCHEMA`-объединение колонок обоих форматов, ветвление построчное.**
Переименовано по просьбе пользователя: класс обслуживает партнёра LT
(«LevelTravel»), а не только Getblogger-формат — так понятнее его роль.
Отсутствующие в конкретном файле ключи `Spreadsheet::Reader` вернёт как
`nil`, поэтому объединённая схема безопасна для обоих форматов; конкретные
поля выбираются через `||` между колонками двух форматов, без явной
проверки, какой это формат. `partner_id`/`partner_name`/`organization_name`
из универсального формата игнорируются — источник истины для `partner_id`
операции — `order.partner_id`, а не колонки файла.

**Для 1163 (`ozon_api`) — переиспользование `OzonApi` без изменений; для
1193 (`CRPO_PP`) — новый класс `CrpoPP`, а не переиспользование `Crpo`.**
`OzonApi` у 1163 уже настроен и его код трогать не нужно. Пользователь
явно попросил имя `CrpoPP` для партнёра 1193 (точнее отражает `CRPO_PP` и
не пересекается с не относящимся к задаче партнёром 1044 `CRPO`) — заведён
отдельный пустой класс-наследник `GeneratedRegistries`; существовавший
ранее пустой класс `Crpo` остался как был, никому не назначен. Партнёров
1044/1150 не трогаем — они не относятся к задаче.

**Значения `registry_processor` — точное PascalCase-имя класса, не
snake_case.**
Первая версия рейк-таска хранила `"alfa_travel"`, `"crpo"` и т.п. Реальная
конвенция в проекте (`TBank`, `Sber`, `OzonApi`, `GeneratedRegistries`) —
хранить сразу имя класса; `Partner#class_registry_processor` просто
вызывает `.camelize`, которое на уже-PascalCase строке не меняет её
(проверено в rails runner для всех 7 значений, включая `CrpoPP`). Rake task
переписан на `"LevelTravel"`, `"AlfaTravel"`, `"Mosgortur"`, `"CrpoPP"`,
`"YandexTravel"`, `"TTravel"`, `"Tutu"` и повторно прогнан в dev.

**Т-Путешествия (1190) получает класс `TTravel`, не `TbankTravel`.**
Существующий `Rules::TBank` — RRN-based класс для Тинькофф-партнёров
(973/1173/1249) с совершенно другой схемой колонок. Хотя технической
коллизии имён нет, `TbankTravel` визуально путается с `TBank` при чтении
кода/логов; выбрано отличимое имя.

**Назначение `registry_processor` — rake task, не data-миграция.**
Таск (namespace `partner_registries`, по образцу `lib/tasks/partner.rake`)
с явным списком `id → registry_processor`, вызывается вручную в нужном
окружении. В отличие от Rails-миграции, он не выполняется автоматически при
деплое — включение обработки для реального партнёра в production остаётся
осознанным решением того, кто его запускает, а не побочным эффектом
раскатки кода. При этом сам таск версионируется и ревьюится вместе с
остальным кодом задачи.

**Фильтрация по статусу заказа — не делаем.**
В образце «Партнёрские программы» встретился `canceled`-заказ с ненулевой
комиссией; реестр партнёра — источник истины по тому, что он платит,
фильтрация на нашей стороне рискует потерять реальную комиссию.

**Сокращённый объём тестирования — по явному решению пользователя.**
Без RSpec/ручных проверок `app/admin/registry_files.rb` и без обязательного
зелёного remote gate TeamCity для этой задачи; достаточно фокусных специй на
Rule-классы и миграцию. Снижает покрытие ActiveAdmin-слоя, но это
сознательный компромисс, а не упущение.
