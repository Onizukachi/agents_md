# LT-54780 Загрузчики реестров оплат Академ Онлайн, Отелло и Випсервис (Портбилет)

## Summary

Бухгалтерия получает от Академ Онлайн, Отелло и Випсервиса XLSX-реестры оплат и сейчас заводит ОП по ним вручную. Добавляем три загрузчика в `/admin/operations_loader` по образцу Островка, HBPro и Benoir. Файл нормализуется при загрузке, строки становятся операторскими операциями (`OperatorOperation`). Операции сопоставляются с заказами через Динамику, и по ним создаются ОП на юрлица поставщиков 119, 120 и 121.

Решения, которые нужно знать до чтения остального:
- **Номер для поиска:** Академ — «№ заказа», Отелло — `Booking ID`, Випсервис — «Номер заказа». Випсервис уходит в Динамику с префиксом `O` (`O28636503`).
- **Две организации Динамики.** Бронь ищется в 8 и в 9: 8 — заказы, проданные через ГорТревел (юрлицо пакета 89), 9 — через «Динамические пакеты» (113). У Випсервиса порядок 9 → 8, у Академа и Отелло 8 → 9. Заказ ищется с юрлицом пакета 89 или 113.
- **ОП:** юрлицо поставщика, RUB, курс 1, источник оплаты — депозит, сумма из реестра без вычетов. Тип операции определяется знаком суммы: минус — возврат.
- **Дата ОП:** Академ — дата из заголовка отчёта, Випсервис — «Дата составления отчета», Отелло — дата загрузки реестра. Дата из шапки при загрузке добавляется в строки виртуальной колонкой «Дата отчета».
- **Перед первой загрузкой Академа** вручную удалить ОП «Тур №ET2K8TS [1]» (заказ 367013801).

## Problem

Бухгалтерия получает реестры оплат от трёх поставщиков, работающих через Динамику:
- Академ Онлайн (ООО «АОН.РУ») — ежемесячный отчёт агента;
- Отелло (ООО «ДубльГИС») — выгрузка заказов за период;
- Випсервис (АО «Випсервис», Портбилет) — еженедельный отчёт-сверка по авиабилетам.

Загрузчика для них нет, поэтому ОП создаются вручную или не создаются вовсе. Сейчас на юрлица 119–121 за всё время заведён один ОП.

Реестры устроены по-разному:
- у Академа и Випсервиса над таблицей шапка, а в конце итоговые строки;
- у Отелло есть отменённые заказы с нулевой суммой;
- у Випсервиса один заказ занимает несколько строк, по одной на документ.

Заказы этих поставщиков продаются через два юрлица пакета: 89 и 113. От этого зависит, в какой организации Динамики лежит бронь. С одной парой «организация — юрлицо», как у Островка, ни один заказ Випсервиса не сопоставится.

## Solution

Бухгалтер выбирает поставщика на странице «Загрузка реестров операций» и загружает исходный XLSX без правок. Загрузчик:
1. Находит строку заголовков, отбрасывает шапку, а для Академа и Випсервиса берёт из неё дату отчёта. На предпросмотре видна колонка «Дата отчета».
2. После запуска обработки создаёт по строке с ненулевой суммой одну операцию. Итоговые, пустые и нулевые строки пропускает. Повторная загрузка того же файла дублей не создаёт.
3. Ищет бронь в Динамике по номеру поставщика, перебирая организации в порядке поставщика, затем находит заказ.
4. По найденным заказам создаёт ОП на юрлицо поставщика: оплата при плюсе, возврат при минусе.

Строки, которые сопоставить не удалось, остаются операциями с ошибкой и видны в существующем логе загрузчика. Ни Островок, ни HBPro, ни общий механизм сопоставления не меняются.

## Current system state

**Конвейер загрузки**
- Страница загрузки: `app/admin/operator_operations/operations_loader.rb`.
  - `upload_register` (`:13`) вызывает `Accounting::OperationsLoader::FileProcessor#process`, который сохраняет нормализованный файл в `AccountingFile`.
  - `process_operations` (`:66`) ставит в очередь `Accounting::OperatorProcessorWorker` с аргументами `{ file:, report_id: }`.
  - `get_requirements` (`:76`) показывает исходные регулярки `MATCHING_COLUMNS` как обязательные колонки.
- `FileProcessor` (`app/services/accounting/operations_loader/file_processor.rb`):
  - читает файл через `XLSXReader`, пишет новый XLSX из строки заголовков и прошедших фильтр строк, все значения строками (`:26-50`);
  - ищет строку заголовков по регуляркам только для EHolidays (`header_matchers`, `:115-119`), у остальных заголовки — первая строка;
  - разбирает даты через `Accounting::<Поставщик>::RegisterValueParser#operation_date`, если такой модуль есть (`:149-156`);
  - сам `reader` при каждом вызове создаётся заново (`:107-113`).
- `XLSXReader` (`app/services/accounting/operations_loader/xlsx_reader.rb`):
  - читает первый лист, значения ячеек приводит к строке (`cell.value.to_s.strip`);
  - строки до заголовка пропускает и не сохраняет;
  - если заголовок не найден, бросает `Roo::HeaderRowNotFoundError`.
- `Accounting::OperatorOperationsProcessor` (`app/services/accounting/operator_operations_processor.rb`) выполняет этапы `PROCESSOR_STAGES_SEQUENCE`. Ошибки сопоставления пишет в операцию (`add_error`) и в `OperatorOperationLog` (`:51-60`). Если в ответе Динамики «response code: 500», бросает исключение, чтобы воркер повторил попытку (`:131-133`).

**Извлечение**
- `Accounting::GrossOperationsExtractor` (`app/services/accounting/gross_operations_extractor.rb`) — основа Benoir, Alean и EHolidays:
  - разбирает файл через `Roo` по `MATCHING_COLUMNS`;
  - `external_id` строит как SHA256 от имени поставщика и значений всех колонок `MATCHING_COLUMNS`, суммы по модулю (`:85-93`).
- `OperatorOperation.create_record` ищет существующую запись по `external_id`, `operator_id`, `operation_type`, `supplier_id` (`app/models/concerns/operator_operations/register_methods.rb:20-24, 72-77`), так что повторная загрузка того же содержимого дублей не даёт.
- Benoir (`app/services/accounting/benoir/extractor.rb`) — пример загрузчика без даты операции: `operation_time: Time.current`; тип операции определяется знаком суммы.

**Сопоставление**
- `Accounting::DynamicsEnricher` (`app/services/accounting/dynamics_enricher.rb`):
  - запрашивает бронь у `OperatorAPI::Leveltravel::Clients::BookingInfoBySupplierOrderId` с одной `organization_id` (`:46-55`), а любую ошибку логирует и пробрасывает;
  - заказ ищет через `Order.by_operator_booking_id(booking_id, operator_id, order_supplier_id)`;
  - валюта по умолчанию `RUB`, курс `1` (`:79-85`).
- `Order.by_operator_booking_id` (`app/models/order.rb:248`) фильтрует по `packages.operator_organization_id`, поэтому принимает и список.
- Ненайденная бронь приходит от Динамики как `OperatorAPI::Leveltravel::Client::ApiError` с текстом «…booking info by supplier order id: booking not found». Ошибки HTTP — как «HTTP request failed, response code: N» (`app/apis/operator_api/leveltravel/client.rb`).
- Юрлица и организации:
  - `OperatorOrganization::DYNAMIC_PACKAGES_ID = 113` (`app/models/operator_organization.rb:5`);
  - организации Динамики перечислены в `app/workers/dinamic_sync_worker.rb:6`: 4 — ГорТревел для ЛТ, 6 — Мосгортур, 8 — Level.travel, 9 — без подписи;
  - на проде 9 — «Динамические пакеты».

**Создание ОП**
- `capture` (`app/models/concerns/operator_operations/capture_methods.rb`):
  - создаёт ОП с `operator_organization_id: supplier_id`, именем «Тур № <бронь>», `paid_at: operation_time`, курсом операции (`common.rb:5-13`);
  - не проверяет, есть ли у заказа ОП, созданные не загрузчиком (`app/models/operator_operation.rb:82-84`).
- Источник оплаты задаёт `OperatorPayment.payment_source_flags_for` (`app/models/operator_payment.rb:154-168`): для Островка, HBPro, Алеана и ГорТревела — депозит, для остальных — платёжное поручение.
- Сумма брутто в ОП идёт только у поставщиков из `gross_amount_operation?` (`common.rb:37-43`). HBPro вместо этого кладёт одну сумму и в нетто, и в брутто.
- Возврат (`refund_methods.rb:27-32`) ищет ОП того же заказа, юрлица поставщика, номера заказа поставщика и валюты, с «Тур» в названии, созданные не раньше `RELEASE_DATE` поставщика.

**Где регистрируется поставщик загрузчика (по Benoir)**
- `Accounting::Constants`: `SUPPLIER_NAMES`, `LOADER_SUPPLIERS[:operations_loader]`, `SUPPLIER_NAMES_BY_IDS`, модуль констант поставщика.
- Модули `Accounting::<Поставщик>::Extractor`, `::Enricher`, `::FileUploader`.

## Scenarios

1. **Академ, обычная загрузка.** Шапка из четырёх строк, заголовки в пятой, в конце строка «Итого».
   - Загрузчик находит заголовки и берёт дату из «Отчет Агента № 4822527 от 30.09.2026 …» — первую дату после «Отчет Агента», а не дату договора.
   - Создаёт одну операцию: номер `15008449` без «.0», сумма 5990, дата 30.09.2026. Строку «Итого» пропускает.
   - Бронь находится в организации 8, заказ с юрлицом 89. ОП: юрлицо 119, RUB, курс 1, депозит, оплачен.
2. **Отелло, обычная загрузка.**
   - Из листа `Orders By Period` создаются операции только по 85 строкам с ненулевой суммой. 11 отменённых заказов с суммой 0 пропускаются.
   - Номер — `Booking ID`, дата операции — момент загрузки. Остальные листы не читаются.
3. **Випсервис, обычная загрузка.**
   - Шапка из пяти строк, заголовки в шестой. Дата операции — «Дата составления отчета» (08.10.2026).
   - Каждая строка документа — отдельная операция, даже если у документов одного заказа совпадают суммы. Итоговые строки «Итого операции …» и «ИТОГО» пропускаются.
   - В Динамику уходит `O28635202`: сначала в организацию 9, потом в 8. Заказ находится с юрлицом 113.
4. **Випсервис, ручная выписка.** Строки заказа 28636503 находят бронь C8XMGM2 по `O28636503` так же, как обычные.
5. **Бронь не найдена ни в одной организации.** Операция остаётся с ошибкой «Не найден booking_id компонента» и записью в логе. ОП не создаётся, остальные строки обрабатываются.
6. **Бронь найдена, но заказа с юрлицом пакета 89 или 113 нет.** Ошибка «Заказ с operator_booking_id '…' не найден» или «Не найден внутренний номер заказа», как сейчас.
7. **Отрицательная сумма.** Создаётся операция возврата. ОП для возврата ищется среди ОП того же заказа, юрлица поставщика и номера заказа. «Возврат» и «Обмен» Випсервиса, по договорённости, приходят с минусом.
8. **Повторная загрузка того же файла или перезапуск обработки.** Новые операции и ОП не появляются.
9. **Файл не того поставщика или без нужных колонок.** Загрузка останавливается с ошибкой, ничего не создаётся.
10. **В шапке Академа или Випсервиса не нашлась дата отчёта.** Загрузка останавливается с ошибкой, ничего не создаётся.
11. **Динамика отвечает ошибкой, но не «booking not found»** (500, таймаут). Перебор организаций прерывается, ошибка обрабатывается как сейчас: при 500 воркер повторяет попытку позже.

## Implementation decisions

**Регистрация поставщиков**
- Имена: `AcademOnline` (юрлицо 119), `Otello` (120), `Vipservice` (121), оператор 78.
- Добавляются в список страницы загрузки и в сопоставление «оператор/юрлицо → имя». В список загрузчика с фильтрами не добавляются.

**Константы поставщика** (как у Benoir):
- колонки реестра `MATCHING_COLUMNS`, регулярки с якорями по целой строке:
  - Академ: «№ заказа», «ID услуги», «Стоимость реализации» с любым пробельным символом между словами, «Дата отчета»;
  - Отелло: `Booking ID`, `Amount`;
  - Випсервис: «Номер заказа», «Номер документа», «Итого (сумма + сборы системы)», «Дата отчета»;
- упорядоченный список организаций Динамики: Академ и Отелло `[8, 9]`, Випсервис `[9, 8]`;
- список юрлиц пакета для поиска заказа: ГорТревел (89) и `OperatorOrganization::DYNAMIC_PACKAGES_ID` (113);
- поля сопоставления: бронь, заказ, валюта, курс;
- этапы: извлечение, сопоставление, управление;
- дата выпуска для поиска ОП при возврате;
- ключи S3 и Redis для загрузки файла.

**Дата отчёта**
- Общая константа с названием виртуальной колонки — «Дата отчета».
- `XLSXReader` сохраняет строки над заголовком и отдаёт их наружу.
- У Академа и Випсервиса есть модуль разбора значений реестра (`RegisterValueParser`): `report_date(строки шапки)` и `operation_date(значение)` для формата `ДД.ММ.ГГГГ`.
  - Академ берёт первую дату после «Отчет Агента … от».
  - Випсервис — значение рядом с «Дата составления отчета».
- Если у поставщика есть `report_date`, `FileProcessor` вычисляет её один раз и добавляет колонку «Дата отчета» в каждую непустую строку. Если дата не найдена, бросает ошибку.

**Поиск строки заголовков**
- Включается для новых поставщиков вместе с EHolidays — через новый список в `LOADER_SUPPLIERS`, а не через сравнение с одним именем.
- Виртуальная колонка в поиске заголовков не участвует.
- Список обязательных колонок на странице загрузки её тоже не показывает. Вычисляется в одном месте и используется и страницей, и поиском заголовков.

**Общий модуль извлечения** для трёх поставщиков, поверх `GrossOperationsExtractor`:
- строка вставляется, если есть номер заказа и ненулевая сумма — так отсекаются итоговые, пустые и нулевые строки;
- тип операции по знаку суммы, модуль суммы кладётся и в нетто, и в брутто (как у HBPro), поэтому список `gross_amount_operation?` не меняется;
- `currency: 'RUB'`, `currency_rate: 1`;
- у номера заказа срезается хвост «.0»: Excel хранит числовые номера с дробной частью;
- дата операции — из колонки «Дата отчета». Отелло переопределяет её на момент загрузки.
- `external_id` — штатный хеш содержимого по `MATCHING_COLUMNS`. Поэтому «Номер документа» Випсервиса и «ID услуги» Академа входят в колонки: они различают строки одного заказа с одинаковой суммой.

**Общий модуль сопоставления** поверх `DynamicsEnricher` (сам `DynamicsEnricher` не меняется):
- ищет бронь, перебирая организации поставщика по порядку;
- ошибку «booking not found» считает промахом и переходит к следующей организации, любую другую ошибку пробрасывает;
- если бронь не найдена ни в одной организации, срабатывает штатная ошибка «Не найден booking_id компонента»;
- заказ ищет по списку юрлиц пакета;
- номер для Динамики получает через переопределяемый метод. Випсервис добавляет префикс `O`, а в операции номер хранится как в реестре.

**Источник оплаты.** 119, 120 и 121 добавляются в список депозитных поставщиков `OperatorPayment.payment_source_flags_for`.

## Testing decisions

- **Одна точка на поставщика** — путь «загрузка + обработка», как в админке:
  1. `FileProcessor#process` на XLSX, собранном в спеке (`Axlsx`) по форме реального реестра: шапка, заголовки, ячейки-числа и ячейки-даты, итоговые строки. Персональных данных нет.
  2. `Accounting::OperatorOperationsProcessor.call(<поставщик>, { file: <нормализованный файл>, report_id: })` с заглушкой `Accounting::DynamicsEnricher::DYNAMICS_API`.
  3. Проверяются только внешние результаты: какие операции созданы, с каким номером, суммой, датой и типом; какие ОП созданы, с каким юрлицом, суммой, курсом, валютой и источником; какие операции остались с ошибкой.
- **Что покрываем:**
  - Академ: шапка, дата из заголовка, «.0», «Итого»;
  - Отелло: пропуск нулевых строк, дата загрузки;
  - Випсервис: дата из шапки, строки по документам, итоговые строки, префикс `O`, порядок организаций с переходом с 9 на 8, юрлицо 113;
  - ненайденная бронь, отрицательная сумма → возврат на ОП оплаты, повторная загрузка без дублей.
- **Образцы:**
  - `spec/services/accounting/operator_operations_processor_spec.rb` — полный конвейер на MyAgent;
  - `spec/services/accounting/benoir/extractor_spec.rb` — дата загрузки, знак суммы, повторная загрузка;
  - `spec/services/accounting/e_holidays/enricher_spec.rb` — заглушка `DYNAMICS_API`, заказы с юрлицом пакета.
- **Запуск:** спеки новых загрузчиков и затронутых модулей локально в контейнере `lt.rails`. Полный прогон CI не нужен (решение пользователя).
