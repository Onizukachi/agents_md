# Реестр альфа миль (Alfa Miles Report)

## Problem

Alfa Bank co-branded miles bonus operations (`PartnerBonus` records with `kind: alfa_miles`) currently produce no outbound reconciliation registry. Alfa Bank needs a daily list of "purchase" (miles debited) and "return" (miles refunded) operations to reconcile against its own records. Today this data only exists implicitly as `PartnerBonus#status` transitions: there is no persisted record of *when* each transition happened, and no mechanism that can produce "yesterday's operations" without risking missing or duplicate rows on retries, redeploys, or worker downtime.

## Solution

A new dedicated model records one row per reportable `PartnerBonus` event — a confirm produces a `'Покупка в ТСП'` row, a refund (of a previously-confirmed bonus) produces a `'Возврат/отмена покупки в ТСП'` row. A daily Sidekiq worker, scheduled like the other daily jobs in `lib/schedule.rb`, finds `PartnerBonus` records confirmed/refunded up through the end of the previous calendar day that don't yet have a corresponding row, and creates them — guarded by a uniqueness constraint so any re-run (retry, backfill after downtime) never duplicates a row. `confirmed_at`/`refunded_at` timestamps are added to `partner_bonuses` as the source of truth for when each transition happened. A secondary, on-demand XLSX export (admin-triggered) lets staff download the accumulated registry for a chosen date range, mirroring the existing `PaymentExportReportBuilder` pattern.

## Scenarios

1. A `PartnerBonus` transitions `created → confirmed` (yesterday or earlier, not yet reported) → a `'Покупка в ТСП'` row is created: `operation_date` = the bonus's `confirmed_at`, `processing_date` = the day the worker ran, `amount` = `partner_bonus.amount`, `order_id` = `partner_bonus.order_id`.
2. A `PartnerBonus` that already has a purchase row later transitions `confirmed → refunded` → a `'Возврат/отмена покупки в ТСП'` row is created in addition to (not instead of) the earlier purchase row, dated by `refunded_at`.
3. A `PartnerBonus` transitions `created → cancelled` (refunded before ever being confirmed) → no row is ever created — no purchase was reported, so there's nothing to reverse.
4. A `PartnerBonus` stays in `pending`, `processing`, or moves to `failed` → no row is ever created.
5. The worker runs twice for the same transition (retry, redeploy, manual re-trigger, or catch-up after downtime spanning multiple days) → no duplicate rows; the uniqueness constraint (or an idempotent find/create) makes every run since the last successful one a no-op for already-reported transitions.
6. Staff trigger the on-demand export for an arbitrary date range from the admin → an XLSX file is produced with columns `order_id, processing_date, operation_date, operation_type, amount`, refund rows shown with a negative amount, purchase rows positive.

## Implementation decisions

- **New table/model**: `alfa_miles_report_entries` / a namespaced model such as `PartnerBonuses::AlfaMiles::ReportEntry`. Columns: `partner_bonus_id` (FK, not null, indexed), `order_id` (denormalized from `partner_bonus.order_id`, avoids a join on every report read), `operation_type` (string, one of the two literal values), `amount` (always positive, mirrors `PartnerBonus.amount`), `operation_date`, `processing_date`. Unique index on `(partner_bonus_id, operation_type)` — this is the sole idempotency mechanism; a `PartnerBonus` can produce at most one purchase row and at most one refund row, ever, regardless of how many times or how late the generation step runs.
- **New columns on `partner_bonuses`**: `confirmed_at`, `refunded_at` (datetime, nullable). Set in `confirm_order.rb` at the same point `partner_bonus.confirmed!` is called (line 33), and in `refund_order.rb` at the same point `partner_bonus.refunded!` is called (line 32) — only on the `confirmed? → refunded` branch; the `created? → cancelled` branch does not need a timestamp since it never produces a report row.
- **Generation service**: selects `PartnerBonus` rows where `confirmed_at` or `refunded_at` is present and falls before the start of the current calendar day, and that lack a matching `ReportEntry` for the corresponding `operation_type` — not a strict "yesterday only" window. This makes the job naturally resilient to the worker missing a day (downtime, deploy) without needing separate backfill tooling: a late run simply reports the missed operations with their true `operation_date` and a `processing_date` equal to whenever it actually ran.
- **Worker + schedule**: a new Sidekiq worker invoking the generation service, added to `lib/schedule.rb` as `every(1.day, at: '<time>am') { worker(...) }` — runs every calendar day, no business-day/weekend exclusion (confirmed: no `business_time` involvement).
- **XLSX export**: a new builder mirroring `PaymentExportReportBuilder` (same `axlsx` dependency, same "Реестр ..." sheet-naming convention), taking a date range and filtering `ReportEntry` by `processing_date`, with the sign of `amount` flipped for refund rows at output time (not stored negative) — same convention as `PaymentExport.export_query`. Triggered from a new admin page analogous to `app/admin/payment_export_reports.rb`.
- No `payment_id` anywhere in this feature — `PartnerBonus` is order-scoped, not payment-scoped, and there is no requirement from Alfa Bank's side establishing a fixed file format that would force keeping an empty column.

## Testing decisions

- Primary seam: the generation service, e.g. `spec/services/partner_bonuses/alfa_miles/report_entries/generate_spec.rb`. Build `PartnerBonus` fixtures (extend `spec/factories/partner_bonuses.rb` with `confirmed_at`/`refunded_at` traits) covering each scenario above; assert the resulting `ReportEntry` rows (type, amount, dates) and assert a second call is a no-op. This is external behavior (what rows exist afterward), not implementation details of how the query is built.
- Extend `spec/services/partner_bonuses/alfa_miles/confirm_order_spec.rb` and `spec/services/partner_bonuses/alfa_miles/refund_order_spec.rb` to assert `confirmed_at`/`refunded_at` get set on the relevant successful transition — these are existing seams, not new ones.
- Secondary seam: the XLSX builder, e.g. `spec/services/partner_bonuses/alfa_miles/report_entries/xlsx_builder_spec.rb`. Assert on the data/rows the builder computes for a given date range (columns, values, refund sign), not on parsing the generated XLSX bytes.
- No controller/admin-level spec — matches the existing precedent that `app/admin/payment_export_reports.rb` and `PaymentExportReportBuilder` have none either.

## Out of scope

- Actually delivering/transmitting the file to Alfa Bank (email, SFTP, API) — no channel or requirement for this has been established; the on-demand XLSX is for staff to act on manually if needed.
- A Russian public-holiday calendar for "business day" logic — the worker runs every calendar day, weekends included, so no `business_time`/holiday-calendar work is needed.
- Backfilling `confirmed_at`/`refunded_at` (and report rows) for `PartnerBonus` records that transitioned before this feature ships — there is no reliable source to reconstruct their exact transition timestamps from.
- Any change to `PaymentExport`/`payment_exports` or its report builder/admin — this feature only borrows established vocabulary and conventions from it, it does not touch it.

## Further notes

- Terminology: this feature is **Alfa Miles Report** in CONTEXT.md — deliberately distinct from **Registry File**, which is the opposite (inbound) direction.
- The `operation_type` values and the `processing_date`/`operation_date` split are not arbitrary: they mirror `PaymentExport`'s existing vocabulary and semantics for card-acquiring registries almost exactly (see `PaymentExport::OPERATION_TYPES` and `PaymentExportReportBuilder::XLSX_HEADER`), which is why they were kept even though this is a new, separate model.
