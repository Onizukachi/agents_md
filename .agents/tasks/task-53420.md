# Привязка юр лиц операторов к городам вылета

Tracker: LT-53420

## 1. Бизнес-контекст

Юридическое лицо оператора (`OperatorOrganization`) — сторона договора, которая
проставляется в пакет и дальше определяет версию договора, чеки, сплит-платежи и
взаиморасчёты. Сейчас юр лицо выбирается только по **стране прилёта**: у юр лица
есть список стран, и пакет получает то юр лицо, чья страна совпала со страной
отеля.

Бизнес работает по документам, в которых указано не только направление, но и
**город вылета**: одно юр лицо оператора продаёт туры из Москвы, другое — из
Санкт-Петербурга, третье — из любого города. Формулировки в документах бывают
двух видов: «работает по городам N» и «работает по всем городам, кроме N».
Сейчас это невыразимо, и все пакеты оператора уходят на юр лицо, подобранное
только по стране, — то есть на юридически неверную сторону договора.

Ожидаемое поведение: город вылета пакета участвует в выборе юр лица наравне со
страной прилёта, причём более специфичная настройка выигрывает у менее
специфичной.

Пример из постановки: «Мегатревел» — Москва → Египет, Турция; «Гигатревел» —
Санкт-Петербург → Турция; «Вездетревел» — откуда угодно → Турция, Египет,
Таиланд, ОАЭ. Тогда Москва→Турция даёт Мегатревел, Питер→Турция — Гигатревел,
Москва→Таиланд — Вездетревел.

## 2. Результат и границы задачи

### Ожидаемый результат

- В карточке юр лица оператора можно задать режим работы по городам вылета:
  все города / только выбранные / все кроме выбранных.
- Новый пакет получает юр лицо с учётом города вылета по правилам из раздела 4.
- Пакет, у которого сменили город вылета или оператора, пересчитывает юр лицо.

### Входит в задачу

- Миграция: режим и связь юр лица с городами вылета (`places`).
- Модель `OperatorOrganization`: ассоциация, enum режима, валидации, предикат
  доступности города.
- Query-объект с алгоритмом выбора юр лица; применение в `Package`.
- Исправление порядка колбэков `Package`, из-за которого версия договора
  считается по старому юр лицу.
- Sentry-предупреждение при срабатывании фолбэка вопреки запрету города.
- ActiveAdmin: режим и список городов в форме, index и show.
- Русские переводы модели, атрибутов и ошибок валидации.
- Тесты: query-объект, колбэки `Package`, валидации `OperatorOrganization`.

### Не входит в задачу

- Бэкфилл и массовый пересчёт юр лиц у существующих пакетов.
- Режимы `only`/`except` для стран прилёта — отдельная задача.
- `PaymentBuilder#operator_organization` — остаётся на старой логике.
- Тесты на админку.
- Изменения сериализаторов и CSV-каталога: они отдают только
  `id/name/phone/inn/operator_id`, география там не фигурирует.

### Критерии готовности

- Сценарии из постановки (Мегатревел / Гигатревел / Вездетревел) и сценарий
  «все кроме Питера» покрыты тестами query-объекта и проходят.
- Юр лицо с непустым списком `only`, который не совпал с городом пакета, не
  выбирается ни на одном шаге.
- Город вылета из списка исключений не даёт выбрать юр лицо на географических
  шагах, но не блокирует финальный фолбэк; фолбэк пишет предупреждение в Sentry.
- В админке режим и города сохраняются, валидации отдают внятное сообщение.
- Миграция применена, `db/schema.rb` содержит только релевантные изменения.
- Локальные тесты зелёные, пройден read-only review, remote gate TeamCity зелёный.

### Предположения

- `package.departure_id` всегда заполнен: в модели есть
  `validates_presence_of :departure`.
- Города вылета выбираются из `Place.departures` — это тот же набор, который
  клиент видит в поиске; он включает не только `kind: 'City'` (например,
  Казахстан, `Place::DEPARTURE_COUNTRY_KZ`).

### Открытые вопросы

- Нет.

## 3. Текущее устройство системы

- Выбор юр лица для пакета: `Package#update_operator_organization`
  (`app/models/package.rb:1280`), вызывается из `after_create
  :set_operator_organization` и `before_update ... if:
  :will_save_change_to_operator_id?` (`app/models/package.rb:76-77`).
  Порядок шагов: сертификатный отель → `external_id` из
  `misc_data`/`pb_tour` → страна прилёта → фолбэк `OperatorOrganization.active`.
- Страны юр лица — это таблица `countries` (модель `CountryOld`) через
  `countries_operator_organizations`; сопоставление идёт **по `name_ru`** со
  страной пакета, которая на самом деле `Place`. Города вылета живут в `places`,
  поэтому «по аналогии» переиспользовать связь нельзя — нужна отдельная.
- Фильтры различаются: шаг по стране использует колонку `active: true` без
  `main`, а финальный фолбэк — scope `OperatorOrganization.active`, то есть
  `main: true AND active: true`.
- Логика продублирована в трёх местах:
  - `Package#update_operator_organization` (`app/models/package.rb:1280`);
  - `Package#detected_operator_organization` (`app/models/package.rb:1342`) —
    те же географические шаги, но для другого оператора (внешняя динамика), без
    сертификата и `external_id`;
  - `PaymentBuilder#operator_organization`
    (`app/services/payment_builder.rb:117`) — свой SQL с
    `countries.name_ru = ? OR operator_organizations.main = ?`.
- `update_operator_organization` пишет результат через `update_columns`: запись
  идёт мимо dirty-tracking и paper_trail, поэтому смена юр лица не попадает в
  версии.
- Rails выполняет всю цепочку `before_save` до `before_update`, поэтому
  `assign_operator_agreement_version` (`app/models/package.rb:78`,
  `OperatorAgreementManager`) считает версию договора по **старому**
  `operator_organization`. Существующий дефект, который задача усугубила бы
  вторым триггером.
- `app/queries/` в проекте есть (пока только `hotel_editor/`), по CLAUDE.md
  read-only выборки живут там.
- Фабрика `spec/factories/operator_organization.rb`; специфических тестов на
  выбор юр лица в пакете сейчас нет.

## 4. Ключевые решения

**Отдельная связь на `places`, а не переиспользование стран.**
Страны юр лица — `countries`/`CountryOld`, города вылета — `places`. Общей
таблицы нет, сопоставление по `name_ru` для городов повторять не нужно.
Последствие: у юр лица две независимые географические настройки с разной
механикой.

**Режим + один список вместо двух списков.**
Колонка `departures_mode` (строковый enum `all` / `only` / `except`, default
`all`) + join-таблица `departures_operator_organizations`. Ложится один в один
на формулировки документов бизнеса, делает бессмысленную комбинацию «и только, и
кроме» непредставимой и показывает режим явным полем. Отвергнуто: флаг
`excluded` на строках связи (порождает вопрос «что если город в обоих
списках») и неявный вывод режима из содержимого таблицы.

**Включение — признак, исключение — вето.**
Список `only` — позитивный признак специфичности и поднимает юр лицо в
ранжировании. Список `except` ничего не говорит о разрешённых городах, поэтому
работает только как фильтр и в ранге равен «без ограничений». Следствие: при
совпадении по стране юр лицо с исключениями и юр лицо без ограничений равны,
спор решает `priority`.

**Итоговый алгоритм.**
1. Сертификатный отель → `OperatorOrganization.lt`.
2. `external_id` из `misc_data`/`pb_tour` (сильнее любой географии: оператор
   явно назвал своё юр лицо).
3. Вето: отбросить юр лица, у которых город вылета пакета в исключениях.
4. Ранжирование, внутри ранга `priority DESC`, фильтр `active: true` без `main`:
   а) `only` совпал и страна совпала;
   б) `only` совпал, страны не заданы;
   в) города не ограничены, страна совпала (старая логика);
   г) города не ограничены, страны не заданы.
   Юр лицо с непустым `only`, который не совпал, выбывает целиком.
5. Фолбэк `OperatorOrganization.active` (`main: true`).

**Фолбэк игнорирует вето и сигналит в Sentry.**
Пакет без `operator_organization_id` — это отсутствующая версия договора,
поехавшие чеки и взаиморасчёты. Формально запрещённое юр лицо с видимым
предупреждением дешевле, чем молчаливый `nil`.
Компромисс: в редком случае «настройки противоречат проданному туру» пакет
получит юр лицо, которое бизнес запретил; сигнал уровня `warning` с
`package_id / operator_id / departure_id` должен привести к правке настроек.

**Единственная точка чтения — `allows_departure?`.**
`org.departures` при режиме `except` содержит города, где юр лицо как раз **не**
работает, и прямое чтение ассоциации почти наверняка будет прочитано неверно.
Наружу отдаём предикат и скоуп, а не список.

**Алгоритм — в `app/queries/`, с двумя входами.**
`OperatorOrganizations::ForPackageQuery`: полный вход для
`Package#update_operator_organization` и только-география для
`detected_operator_organization`. Разница сохраняется намеренно: `external_id`
приходит от исходного оператора и не должен участвовать в подборе юр лица
внешнего поставщика динамики.

**`PaymentBuilder` не трогаем.**
Там свой набор фильтров (`OR main = true`), он уже может отдать не то юр лицо,
что стоит в пакете. Задача расхождение не чинит, но и не маскирует — риск
зафиксирован в разделе 7.

**Чиним порядок колбэков.**
`before_update :update_operator_organization` → `before_save`, объявленный выше
`assign_operator_agreement_version`, с обычным присваиванием вместо
`update_columns`; триггер `will_save_change_to_operator_id? ||
will_save_change_to_departure_id?`. Иначе новый путь «сменился город вылета»
оставит версию договора рассинхронизированной с юр лицом, а изменение не попадёт
даже в paper_trail.
Последствие: в paper_trail появятся записи по `operator_organization_id`,
которых раньше не было.

**Без бэкфилла.**
Пересчёт юр лиц у уже забронированных и оплаченных пакетов задним числом меняет
сторону договора в чеках и взаиморасчётах. Существующая
`rake packages:set_operator_organization` при необходимости запускается вручную
и осознанно.
