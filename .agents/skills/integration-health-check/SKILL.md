# Integration Health Check

Проверяй здоровье сервисов через skill `lvtv-elastic-logs` и отвечай наблюдаемыми фактами, а не только наличием логов. Для каждой проверки показывай общий статус и детализацию по поставщикам там, где она есть.

## Scope

Для запроса о `currency` используй профиль `integrations` и индекс `fbyc-currency-*`. По умолчанию анализируй `now-3h`—`now`. Для определения новых ошибок сравнивай этот интервал с тем же трёхчасовым интервалом шесть дней назад.

Подробные поля, запросы и правила классификации находятся в [references/currency.md](references/currency.md). Прочитай этот reference перед анализом `currency`.

Для запроса о `booker` используй профиль `integrations` и индекс `fbyc-booker-*`. Прочитай [references/booker.md](references/booker.md) перед анализом `booker`.

Для запроса о `searcher` используй профиль `integrations` и индекс `fbyc-searcher-*`. Прочитай [references/searcher.md](references/searcher.md) перед анализом `searcher`.

Для запроса о `storage` используй профиль `integrations` и индекс `fbyc-storage-*`. Прочитай [references/storage.md](references/storage.md) перед анализом `storage`.

Для запроса о `actualizer` используй профиль `integrations` и индекс `fbyc-actualizer-*`. Прочитай [references/actualizer.md](references/actualizer.md) перед анализом `actualizer`.

## Required response

Отчёт должен быть максимально коротким: нормальные сервисы перечисляй одной строкой, подробно показывай только новые или подтверждённые проблемы. Для Booker/Searcher используй однозначный формат `ошибки / успешные, всего попыток (процент ошибок)` и добавляй безопасную причину конкретного сбоя.

Сначала дай короткий вывод:

- `currency работает` — если ошибки `GetRate` отсутствуют и в pulling rates нет новых ошибок;
- `currency работает частично` — если есть только известные ошибки pulling rates;
- `есть проблемы в currency` — если появились новые ошибки pulling rates или есть ошибки при получении rate из сервиса.

Затем укажи:

1. временное окно текущей проверки и профиль/индекс;
2. состояние запросов получения rate из сервиса;
3. состояние pulling rates;
4. список поставщиков: успешные события, ошибки, известна ли ошибка по сравнению с интервалом шесть дней назад;
5. новые ошибки с количеством, временем последнего события и краткой безопасной причиной.

Не называй сервис полностью здоровым только потому, что в нём есть свежие логи. Если данных для проверки недостаточно, явно сообщи об этом.

Если все ошибки pulling rates в currency совпадают с контрольным окном, полностью игнорируй их в тексте и пиши только `currency работает`. Не перечисляй известные ошибки отдельно.

## Safety and interpretation

- Считай `json.grpc.method=GetRate` успешным только при `json.grpc.code=OK`; любой другой код — проблема.
- Не приписывай ошибку `GetRate` поставщику, если в записи нет поля поставщика.
- Для pulling rates связывай поставщика и причину из `json.error` в формате `failed to pull rates from PROVIDER: REASON`.
- Ошибка pulling считается известной только при совпадении поставщика и нормализованной причины с записью в контрольном окне шесть дней назад. Новая комбинация — проблема.
- Ошибки получения rate из сервиса всегда считаются проблемой, даже если они уже встречались шесть дней назад.
- Скрывай токены, query-параметры, полные URL и другие секреты из `json.error`, `json.url` и `message`; показывай только hostname, HTTP-код и безопасную текстовую причину.
- Отделяй факт от вывода: указывай количество событий и поля, на которых основана классификация.
- Не объявляй проблему из-за одной изолированной ошибки: показывай её в детализации как единичную, но не ухудшай общий статус. Это правило не распространяется на panic и на повторяющиеся/массовые ошибки.

## Panic check for every supported service

Для каждого анализируемого сервиса и его индекса отдельно ищи panic в `message`, `json.msg`, `json.error` и `json.stacktrace`, включая варианты `panic:`, `panic(` и `runtime error`. Любое найденное panic — проблема независимо от остальных метрик, кроме явно указанного в reference исключения для actualizer: `panic: failed to sync logger` не включай в отчёт. Показывай количество, время последнего события, сервис, pod и безопасный фрагмент причины.

## Future expansion

Не делай выводы о `go-tour`, `storage` или `actualizer` по правилам `currency`, `booker` или `searcher`. Для них добавляй отдельные references и отдельные критерии здоровья.
