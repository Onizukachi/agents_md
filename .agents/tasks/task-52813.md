# Надёжное применение скидки АльфаМиль при создании заказа

## Статус реализации

Реализовано в рабочей ветке:

- синхронная первая попытка hold и идемпотентные ретраи только для
  технических ошибок;
- статусы `processing` и `failed`, а также разделение requested/applied
  суммы;
- status-only блокировка актуальных PAPI v3 payment flow без изменений
  frontend;
- переход в полную цену при business failure или после исчерпания retry.

Старый `Papi::V3::UnitellerController` намеренно исключён из объёма задачи.

Проверка: focused RSpec набора прошла; обязательный полный локальный gate
заблокирован доступом Docker к приватному базовому образу `cr.yandex` (403).

## 1. Бизнес-контекст

При создании PAPI v3 заказа клиент может запросить оплату части стоимости
АльфаМилями. Перед сохранением заказа система проверяет баланс, однако это
только чтение и не создаёт холд. Реальный вызов `CreateOrder` в AlfaMiles
сейчас запускается после сохранения заказа асинхронным worker.

Из-за этого сохранённый `PartnerBonus` со статусом `pending` уже участвует в
расчёте скидки, хотя холд в Альфе ещё не подтверждён или мог завершиться
ошибкой. Клиент способен создать платёж на уменьшенную сумму, хотя мили не
были захолдированы.

Альфа гарантирует идемпотентность `CreateOrder`. Это позволяет безопасно
повторять вызов после timeout и сетевых ошибок без отдельного статуса
неопределённости.

## 2. Результат и границы задачи

### Ожидаемый результат

- Скидка АльфаМиль участвует в расчёте цены и платежа только после успешного
  создания внешнего заказа (`created`) или окончательного списания миль
  (`confirmed`).
- При временной ошибке AlfaMiles заказ остаётся с бонусом в `processing`,
  внешний вызов повторяется идемпотентным worker, но оплата со скидкой не
  создаётся.
- При явном отказе Альфы или исчерпании технических попыток бонус переходит в
  `failed`; заказ можно оплатить по полной стоимости.
- Ни один PAPI payment entry point не сможет создать `Payment` со скидкой,
  пока холд не готов.
- Реализация не требует изменений frontend и не добавляет новый публичный API
  контракт.

### Входит в задачу

- Новые статусы и доменные предикаты `PartnerBonus`.
- Разделение запрошенной суммы миль и фактически применённой скидки.
- Синхронная первая попытка `CreateOrder` после сохранения заказа.
- Retry worker только для временных ошибок AlfaMiles.
- Блокировка создания платежа по статусу, пока холд в `processing`.
- Пересчёт локальных финансовых производных после смены статуса бонуса.
- Логи, Sentry и focused specs.

### Не входит в задачу

- Изменения frontend, polling или новый UI для статуса холда.
- Физическое удаление `PartnerBonus`: история запроса должна сохраняться.
- Изменение AlfaMiles API или правила его идемпотентности.
- Ручное исправление уже созданных исторических заказов.
- Изменение флоу подтверждения (`ConfirmOrder`) и возврата (`RefundOrder`),
  кроме адаптации к новым безопасным статусам.

### Критерии готовности

- `pending` и `processing` не уменьшают `Order#price`,
  `Order#remaining_amount` и сумму нового `Payment`.
- `created` и `confirmed` уменьшают цену ровно на запрошенную сумму миль.
- `prebuild` сохраняет существующую предварительную скидку после успешной
  проверки баланса.
- Payload `CreateOrder` содержит запрошенную сумму миль и корректную cash
  часть независимо от того, учитывается ли скидка в локальной цене.
- При timeout или сетевой ошибке первый запрос не приводит к оплате со
  скидкой; повтор идемпотентен.
- Явный отказ не ретраится и переводит бонус в `failed`.
- После исчерпания технических retry бонус переводится в `failed`.
- Во время `processing` ни один поддерживаемый PAPI payment entry point не
  сохраняет `Payment`.
- Без frontend-изменений клиент может повторить оплату: после `created` — со
  скидкой, после `failed` — по полной стоимости.

## 3. Целевая модель состояний

| Статус | Значение | Учитывается как скидка | Действие при оплате |
|---|---|---:|---|
| `pending` | Бонус создан локально, холд ещё не запущен | нет* | Запустить hold-service |
| `processing` | Идёт запрос или ожидается технический retry | нет | Не создавать платёж |
| `created` | Альфа успешно создала заказ и захолдила мили | да | Разрешить оплату |
| `confirmed` | Мили окончательно списаны | да | Штатный последующий флоу |
| `failed` | Явный отказ или исчерпаны технические retry | нет | Разрешить оплату полной суммы |
| `cancelled` | Внешний холд отменён | нет | Штатный флоу без скидки |
| `refunded` | Списанные мили возвращены | нет | Штатный флоу без скидки |

`*` Для несохранённого заказа в `prebuild` действует отдельное правило:
показывается предварительно запрошенная сумма, поскольку холд там намеренно
не создаётся.

### Финансовые методы

```ruby
def requested_partner_bonus_amount
  partner_bonus&.amount.to_i
end

def partner_bonus_amount
  return requested_partner_bonus_amount if new_record?
  return requested_partner_bonus_amount if partner_bonus&.created? || partner_bonus&.confirmed?

  0
end
```

`requested_partner_bonus_amount` выражает намерение клиента и используется
для prebuild и payload в AlfaMiles. `partner_bonus_amount` выражает уже
подтверждённую скидку и остаётся единой точкой для `discount`, `price`,
`discount_price`, `remaining_amount`, `PaymentBuilder`, статистической цены и
партнёрской комиссии.

## 4. Целевой флоу

1. `orders#create` сохраняет заказ и `PartnerBonus` в `pending`.
2. После commit контроллер синхронно запускает hold-service.
3. Сервис под блокировкой переводит `pending` в `processing` и вызывает
   идемпотентный `CreateOrder`.
4. Успешный ответ переводит бонус в `created`, сохраняет `external_id` и
   возвращает заказ со скидкой.
5. Явная бизнес-ошибка переводит бонус в `failed`; `orders#create` возвращает
   заказ с полной стоимостью.
6. Timeout, сетевая ошибка и временный HTTP-ответ оставляют бонус в
   `processing` и ставят retry worker. Ответ
   создания заказа содержит полную стоимость.
7. Перед созданием платежа общий guard только проверяет статус холда. Для
   `pending/processing` он не делает HTTP-вызов в Альфу и не создаёт
   `Payment`; используется существующий формат retryable ошибки платежной
   операции. Все повторные вызовы `CreateOrder` выполняет исключительно
   worker.
8. Retry worker доводит статус до `created` либо до `failed` после исчерпания
   попыток. После `failed` последующая попытка оплаты идёт по полной цене.

## 5. План реализации

- [ ] Шаг 1: описать классификацию ошибок AlfaMiles в одном сервисе.

  Выделить успешный, business-failure и retryable-failure результаты из
  ответов и исключений `TravelClient`. Business-failure не должен попадать в
  Sidekiq retry, а timeout, сетевые исключения и временные 5xx должны
  ретраиться. Это требуется, чтобы терминальный `failed` означал, что скидку
  больше не следует ждать, а не скрывал неизвестный результат запроса.

- [ ] Шаг 2: расширить `PartnerBonus` статусами `processing` и `failed` и
  добавить предикаты.

  В enum строковых статусов добавить новые значения, например `applied?` для
  `created/confirmed` и `payment_waiting?` для `pending/processing`. Для
  строкового enum миграция схемы не требуется. Это формализует единственный источник правды о
  том, можно ли дать скидку или создать платёж.

- [ ] Шаг 3: разделить requested и applied сумму в `Order`.

  Добавить `requested_partner_bonus_amount` и сделать
  `partner_bonus_amount` статус-зависимым, с исключением для несохранённого
  prebuild-заказа. Проверить все текущие потребители: `discount`,
  `discount_price`, `bonuses`, `partner_price`, `price_without_discount`,
  `discount_fully_cover?`, payment methods и сериализацию заказа. Это убирает
  первопричину: существование строки `partner_bonuses` больше само по себе не
  означает скидку.

- [ ] Шаг 4: отвязать payload Альфы от локально применённой скидки.

  В `PartnerBonuses::AlfaMiles::CreateOrder` брать bonus payment из
  `requested_partner_bonus_amount`, а cash payment рассчитывать от полной
  стоимости минус эта requested сумма. `totalSum` должен сохранять текущую
  семантику полной цены заказа. Это необходимо, так как в `processing`
  `order.discount[:price]` и `order.price` уже будут отражать отсутствие
  локальной скидки, но Альфе всё равно нужно передать запрошенные мили.

- [ ] Шаг 5: создать orchestration service для холда и заменить прямой вызов
  worker в `Papi::V3::OrdersController#create`.

  Сервис должен блокировать строку бонуса, выполнять переходы
  `pending -> processing -> created/failed`, сохранять `external_id`, писать
  order log и возвращать типизированный результат. Контроллер делает первую
  синхронную попытку после успешного commit, а при retryable failure ставит
  worker. Это уменьшает окно ожидания и сразу возвращает корректную цену при
  быстром успешном или бизнес-неуспешном ответе.

- [ ] Шаг 6: адаптировать `OrderHandlerWorker` к новой роли retry worker.

  Worker должен обрабатывать только `processing`, повторно вызывать тот же
  orchestration service и не ретраить business failure. В callback
  `sidekiq_retries_exhausted` он переводит бонус в `failed`. Это гарантирует, что заказ
  не остаётся со скидкой вечно и дальнейшая оплата предсказуема.

- [ ] Шаг 7: поставить status-only guard до создания любого `Payment`.

  Найти и покрыть все PAPI v3 entry point’ы, которые создают payment:
  `PayCardMethods#assign_payment!`, `PaymentParamsMethods#payment_params_action`
  / `PaymentDetector` и legacy `OrdersController#pay` с его before action.
  Guard не обращается во внешние сервисы: для `pending/processing` он сразу не
  создаёт `Payment` и возвращает существующую retryable ошибку; для
  `created/confirmed` пропускает оплату, для `failed/cancelled/refunded` —
  пропускает по полной цене. Все вызовы и интервалы retry остаются в
  `OrderHandlerWorker`. Это закрывает гонку между фоновым worker и переходом
  пользователя к оплате, не добавляя сетевую зависимость в критический
  payment-флоу.

- [ ] Шаг 8: корректно обработать устаревшую сумму, переданную frontend.

  Если между ответом `orders#create` и запросом оплаты worker успел создать
  холд, серверная сумма могла уменьшиться. Для card entry point нужно
  использовать пересчитанную серверную сумму, а не ошибочно отклонить запрос
  как `incorrect_price` только потому, что frontend прислал прежнюю большую
  сумму. Это обязательно для backend-only решения без polling на frontend.

- [ ] Шаг 9: обновлять производные финансовые данные после смены статуса.

  После `processing -> created` или `processing -> failed` принудительно
  обновлять/инвалидировать кэш payment methods, `stat_price` и `PartnerCheck`
  там, где они были рассчитаны до итогового статуса бонуса. Это требуется,
  чтобы отчётность, партнёрская комиссия и последующая оплата использовали ту
  же цену, что и заказ.

- [ ] Шаг 10: адаптировать ActiveAdmin и операционные наблюдения.

  В списке и карточке бонуса показывать `processing/failed`. Сохранить ручную возможность безопасно повторить технически
  неуспешный `CreateOrder` при необходимости, но не запускать автоматический
  retry для явного бизнес-отказа. Это даёт операционной команде способ
  расследовать редкие инциденты без удаления финансовой истории.

- [ ] Шаг 11: покрыть матрицу focused tests и выполнить обязательные
  проверки.

  Добавить model/service/worker/controller specs для всех переходов, payload,
  retry и payment gate. Запустить их через project Docker gate по skill
  `leveltravel-tests`; перед возможным push или PR выполнить read-only review
  по `leveltravel-pr-review`. Это проверяет как финансовую математику, так и
  отсутствие регрессии в существующих способах оплаты.

## 6. План проверок

- [ ] `PartnerBonus`/`Order` specs: сумма для `pending`, `processing`,
      `created`, `confirmed`, `failed`, `cancelled`, `refunded` и new-record
      prebuild.
- [ ] `CreateOrder` spec: payload использует requested сумму при `processing`.
- [ ] Hold-service specs: success, business failure, timeout, сетевое
      исключение, повторный идемпотентный вызов и конкурентные обращения.
- [ ] Worker specs: retryable failure остаётся `processing`; исчерпание retry
      переводит в `failed`; business failure не ретраится.
- [ ] PAPI controller specs: успешный синхронный холд, `failed` с полной
      стоимостью, `processing` без скидки и отсутствие `Payment` при
      недоступной Альфе.
- [ ] Payment-flow specs: card, redirect-based payment и legacy `orders#pay`
      не обходят guard; при `processing` не вызывается AlfaMiles service и не
      создаётся `Payment`; устаревшая большая сумма корректно заменяется
      серверной после успешного холда.
- [ ] Проверка отображения статусов в ActiveAdmin.
- [ ] Локальный тестовый gate через
      `.agents/skills/leveltravel-tests/scripts/local_rspec.sh`.
- [ ] Финальный read-only review перед push/PR.

## 7. Открытые решения до реализации

- Зафиксировать перечень Alfa response-кодов, которые считаются business
  failure, и отдельно — retryable failure. Пока классифицировать только по
  наличию поля `error` недостаточно.
- Согласовать лимит и интервалы retry. Текущие две попытки через 1 и 5 минут
  могут быть сохранены как стартовое значение, но после исчерпания обязательно
  нужен переход в `failed`.
- Определить точный формат server-side error при payment guard во время
  `processing`, используя существующие PAPI payment errors, чтобы не менять
  frontend-контракт. Ошибка не должна запускать дополнительный вызов в
  AlfaMiles.
- Подтвердить, должны ли сотрудники ActiveAdmin иметь право вручную повторять
  `failed` бонус.
